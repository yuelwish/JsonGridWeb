# 编辑器搜索的匹配滚动自行实现，不复用编辑器默认的贴边滚动

「编辑器搜索面板」的匹配跳转到视口外时，本项目自行接管滚动：一次查询里第一个需要滚动的匹配落在视口垂直居中，同一查询的后续匹配贴着来向边缘（下方来找底缘、上方来找顶缘）并留出间距，入场走一小段渐次滚动（「从最下方上来一点点」）。不用 CodeMirror 搜索默认的 `scrollToMatch`（其行为是 `EditorView.scrollIntoView(range)`，即 `y: "nearest"` 的贴边可见）——它不居中，而且在虚拟滚动的估算块高下会把匹配甩到视口顶端之外（实测落点 -20px，匹配被上边缘裁切）。

## Considered Options

- **完全照抄源站 Ace 的落点**（`revealRange(range, .5)`，实测首个匹配居中、后续匹配贴底缘）：落点分布（首个居中、后续贴边）与源站一致，但后续匹配留出固定间距并补一小段渐次移动——源站的贴底缘是第二次滚动调用拿到过期滚动值造成的副作用，贴死边缘时可读性差。
- **所有匹配统一居中**：落点可预期，但连续按「下一个」时视口持续大幅跳动，且与源站的手感不一致。
- **后续匹配也用贴边滚动的落点当动画起点**：未渲染区域的估算偏差可达半屏（折行文档实测把匹配甩到视口上边 -20px），动画会退化成「从顶部滑下来」。起点必须按实测内容坐标自己算。
- **让远距离匹配全程无跳变**（逐行渲染几千行）：CodeMirror 对未渲染区域只有估算块高，逐帧渲染会卡顿且画面抖动。接受「内容区域瞬移 + 匹配渐次揭示」，并把它记为已知限制。
- **用浏览器原生平滑滚动**（CSS `scroll-behavior: smooth`）：目标浏览器含 iOS Safari 12+，该属性 15.4 才支持，违反零 polyfill 约束。改为自行用 requestAnimationFrame 驱动。

## Consequences

- 匹配滚动逻辑独立成模块，通过 CodeMirror 官方的 `search({ scrollToMatch })` 扩展点接管，不改第三方库内部。
- 关键约束是「先测量、后落位、再动画」：目标区域未实测前算出的落点是估算值，这正是原缺陷的成因。贴边滚动只用来把目标区域渲染出来，它的落点位置不可信，既不用于方向判定也不用于动画起点。
- 源站本身没有动画（Ace 的 `animatedScroll` 实测为 false，默认关闭），渐次揭示是本项目的增强项而非复刻。
