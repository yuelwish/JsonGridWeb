# Ctrl+F 激活编辑器搜索面板

## Problem Statement

用户在 JSON 编辑器（左侧面板）里按 `Ctrl+F` 时，弹出的搜索界面与项目自己做的「编辑器搜索面板」完全不是同一个东西：前者是 CodeMirror 原生的默认搜索面板，样式突兀、与整体界面不协调；后者是复刻原站 Ace searchbox 的定制面板，点工具栏「搜索」按钮才看得到。

对用户而言这是同一项功能的两个入口给出两副面孔，且快捷键这个更常用的入口恰好是丑的那一副。用户被迫记住「要好看就用按钮，要快就用快捷键」。

## Solution

让 `Ctrl+F`（macOS 为 `Cmd+F`）在 JSON 编辑器内激活同一个「编辑器搜索面板」，与点工具栏「搜索」按钮的行为完全一致：打开面板、完成定制、聚焦输入框。快捷键与按钮收敛为同一入口、同一外观、同一功能集。

浏览器原生查找不再介入编辑器内的查找。编辑器外（例如页面其他区域）浏览器原生查找仍照常工作。

## User Stories

1. As a JSON 用户, I want 在编辑器里按 Ctrl+F 就得到那个好看的搜索面板, so that 我不用改用工具栏按钮也能得到一致体验
2. As a JSON 用户, I want Ctrl+F 与工具栏「搜索」按钮打开的面板长得一模一样, so that 我不需要记住两套 UI
3. As a JSON 用户, I want Ctrl+F 打开的面板自带正则/大小写/全词开关, so that 高级查找不用换工具
4. As a JSON 用户, I want Ctrl+F 打开的面板自带替换行, so that 查找后能就地替换
5. As a JSON 用户, I want Ctrl+F 打开的面板显示匹配计数, so that 我知道命中多少处
6. As a JSON 用户, I want Ctrl+F 打开的面板无匹配时给出红框提示, so that 我立刻知道搜错了而不是页面坏了
7. As a JSON 用户, I want 按下 Ctrl+F 后焦点已在搜索输入框, so that 我可以立刻打字而不必再点一次
8. As a macOS 用户, I want Cmd+F 也能用, so that 我不用为了快捷键切到别的键位
9. As a JSON 用户, I want 搜索面板再次按 Ctrl+F 时不炸、不重复叠加面板, so that 我可以放心反复按
10. As a JSON 用户, I want 搜索面板里原有快捷键（Enter 下一个、Esc 关闭、Shift+Enter 上一个）保持可用, so that 肌肉记忆不失效
11. As a JSON 用户, I want Ctrl+F 在空文档上也能打开面板, so that 我可以先开面板再粘贴内容
12. As a JSON 用户, I want Ctrl+F 在超长 JSON 上也能搜到视口之外的匹配, so that 查找结果可信
13. As a JSON 用户, I want 在编辑器外按 Ctrl+F 时仍是浏览器原生查找, so that 页面其他区域也能用浏览器查找
14. As a 键盘用户, I want 不碰鼠标就能从编辑器进入搜索, so that 查找不打断我的输入流
15. As a 键盘用户, I want 按 Esc 能从搜索回到编辑器正文继续输入, so that 我不必用鼠标点回正文
16. As a 原站对照用户, I want Ctrl+F 的行为与 jsongrid.com 原站一致（原站 Ace 里 Ctrl+F 就是打开搜索框）, so that 我的使用习惯在重构版里不变
17. As a 维护者, I want Ctrl+F 与按钮共用同一段打开逻辑, so that 以后不会再次漂移出两副面孔
18. As a 维护者, I want 搜索面板的定制逻辑保持幂等（重复打开不会叠加 DOM）, so that 反复触发快捷键是安全的
19. As a 维护者, I want 这个改动不新增运行时依赖、不增加产物体积, so that 不触碰项目红线
20. As a 维护者, I want 这个改动不影响紧凑格式化序列化的输出字节, so that `npm run verify` 仍然全绿

## Implementation Decisions

- 快捷键绑定到「编辑器搜索面板」的打开动作，与工具栏「搜索」按钮共用同一个入口函数。两者不再各自调用底层 API，避免行为分叉。
- 编辑器配置中新增一个快捷键绑定，拦截 CodeMirror 内置 `basicSetup` 自带的 `Mod-f`（打开原生搜索面板）绑定。CodeMirror 的 keymap 按扩展声明顺序决定优先级，声明在前者先命中；也可显式提高该绑定的优先级，二者取其一即可，但必须确保覆盖生效且意图明确。
- 拦截后的处理是：打开 CodeMirror 搜索面板、执行既有的面板定制逻辑、返回「已处理」，从而阻止事件继续落到默认绑定。
- 面板定制函数保持现有幂等实现（面板节点上打标记，已定制则直接返回）。快捷键路径复用它，不新增第二份定制代码。
- `Mod-` 前缀由 CodeMirror 归一化，Windows/Linux 为 Ctrl、macOS 为 Cmd，无需按平台分别绑定。
- 只改 CodeMirror 编辑器的键位层，不触碰面板 DOM 结构、样式、定位逻辑，也不触碰 worker 的序列化实现。
- GRID 视图不纳入本次范围。GRID 搜索面板是独立交互（自带防抖、状态行、Limitations 弹窗），其快捷键另作任务。
- 保持零新增依赖：产物仍为单 HTML 文件，不引入任何需要 polyfill 的 API，不使用 ES2019+ 语法。

## Testing Decisions

好的测试只验外部可观察行为：给定一次按键，编辑器内是否出现「编辑器搜索面板」且其外观与按钮路径一致。不测「某段源码里是否存在某个字符串」这类实现细节的等价物，除非该字符串本身是唯一可自动化的行为代理。

本仓库现状：零测试框架（无 playwright/puppeteer/vitest/jest/jsdom），CI 只有 build + deploy，无 test job。唯一先例是 `scripts/verify-compact.mjs`——纯 node 脚本、靠抽取源码片段在沙箱里实例化、以退出码 0/非 0 判定。

据此分两层：

- 自动化（沿用 `verify-compact.mjs` 先例，新增一个同风格的 node 脚本并挂到 npm script）：静态断言编辑器配置中存在一个早于/优先于默认绑定的搜索快捷键绑定，且其处理函数打开了搜索面板并触发了面板定制。这是源码层断言，明确记为「代理断言」——它无法证明浏览器里真的生效，只防止绑定被误删或被覆盖。
- 人工验收（唯一能真正证伪「Ctrl+F 在浏览器里打开定制面板」的手段，因为该行为跨越浏览器按键分发与 DOM 渲染，静态脚本原理上无法覆盖）：
  1. `npm run build`，在 `dist` 上起服务，打开页面。
  2. 点「样例」加载数据，点击 JSON 编辑器正文取得焦点。
  3. 按 `Ctrl+F`：应出现与点「搜索」按钮**完全相同**的面板（三行结构、`Search for` 占位符、`N of M` 计数、`.* Aa \b` 开关、右上角关闭圆钮、贴内容区右上角定位）。
  4. 输入一个文档中存在的串：计数更新，高亮出现，按 Enter 能逐个跳转，Shift+Enter 回退。
  5. 输入一个不存在的串：输入框出现红色无匹配框。
  6. 点 `+`：替换行展开，可执行单个替换与全部替换。
  7. 连按数次 `Ctrl+F`：面板不叠加、样式不塌。
  8. 按 `Esc`：面板关闭，焦点回到编辑器正文。
  9. 点击页面非编辑器区域再按 `Ctrl+F`：出现浏览器原生查找（未被劫持）。
  10. 切暗色主题重复第 3 步：面板配色正确。

回归护栏：`npm run build`（含 `tsc` 类型检查）必须通过；`npm run verify`（紧凑序列化逐字节回归）必须全绿——本改动不触碰 worker，实现上不应影响它，跑它是为了证明这一点。

新增的搜索快捷键静态断言：`npm run verify:search`。它是**源码层代理断言**，只能证明绑定与调用关系存在，无法证明浏览器里按键真的生效；上述人工验收是唯一能证伪浏览器行为的手段。

## Out of Scope

- GRID 视图的 Ctrl+F 快捷键，以及任何跨视图的快捷键路由。
- 面板 DOM 结构、样式、定位（双 rAF 量位）逻辑本身的改动。
- 替换 `customizeSearchPanel` 的 DOM 重组做法为 CodeMirror 官方 `search({ panel })` 自定义面板。当前做法可用，重构风险大于收益。
- 搜索面板视觉细节的微调（配色、间距、按钮形状）。
- 其他快捷键的行为对齐（折叠、跳转行、编辑历史等）。
- 在 CI 中引入浏览器驱动测试框架。
- 移除浏览器原生查找在编辑器外的可用性。

## Further Notes

- 根因一句话：`basicSetup` 内置的 `Mod-f` 直接调 `openSearchPanel`，跳过了定制步骤；定制只在按钮 click 处理器里被调用。两者不是同一个入口。
- 为什么不让浏览器原生查找接管编辑器内查找：CodeMirror 6 只把可视区内的行渲染进 DOM，浏览器原生查找只匹配已渲染的 DOM 文本。大型 JSON 文件的绝大部分内容不在 DOM 中，原生查找会漏匹配甚至误报「未找到」，与项目「高性能大 JSON 工具」的定位直接冲突。这是本次决策的实质理由，不是审美偏好。
- 已被否决的替代方案：删除 `basicSetup` 中的搜索绑定、把 Ctrl+F 让给浏览器。原因同上，且会丢失正则/大小写/全词/替换/计数，与已复刻好的原站 Ace searchbox 功能集不对等。
- 术语见仓库 `GLOSSARY.md`：「JSON 编辑器」「编辑器搜索面板」「GRID 搜索面板」「浏览器原生查找」是四个不同概念，本次改动只涉及前两个与第四个的边界。
- 产物体积红线 150KB gzip，本次改动为纯逻辑、无新依赖，不影响该指标；实现完成后建议顺带核对一次实测值。
- 实现过程中核实过：`basicSetup` 内置的 `searchKeymap` 中**只有 `Mod-f` 会打开搜索面板**，其余绑定（查找下一个/上一个、跳转行、选中下一个匹配、关闭面板）都不打开面板。因此覆盖 `Mod-f` 一个绑定即可堵住全部缺口，无需连带调整其他快捷键。
- 内置绑定的 scope 是 `editor search-panel`，即面板内也命中它。新的绑定声明为编辑器级，面板内的 `Mod-f` 仍走默认绑定；由于面板已开，`openSearchPanel` 无副作用，且 `customizeSearchPanel` 本身幂等（面板节点打了标记），故重复触发安全。
