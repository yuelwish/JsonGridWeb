# 编辑器搜索的匹配落点与揭示滚动：匹配居中、从视口底缘渐次升起

## Problem Statement

在 JSON 编辑器里用「编辑器搜索面板」搜索时，只要命中的匹配落在当前视口之外，界面就会把匹配**硬拽到视口顶端**——而且拽得过头，匹配文本被上边缘裁掉一半（实测落点 y = -20px，视口高度 812px）。

复现路径：加载样例数据 → 打开搜索面板 → 搜索 `true` → 第一个匹配在视口之外 → 它瞬间出现在 JSON 栏的最上方，且被裁切。

用户视角的三个问题叠在一起：跳的过程是瞬时的（单帧从 0 跳到 1065.6px），看不出"它是从哪冒出来的"；落点是视口顶端而不是中间，一眼扫过去容易漏掉；匹配被裁切，看不全。

对照源站 jsongrid.com（Ace 1.31.1）实测：首个匹配落在视口垂直居中（403/840 = 48%），后续落在视口底缘（806/840 = 96%），即"从下方冒出来"。本地重构版与源站在这件事上的差别，正是本次要修的。

## Solution

给「编辑器搜索面板」的匹配跳转引入「匹配落点」与「揭示滚动」：

- **一次查询里第一个需要滚动的匹配落在视口垂直居中**。搜索后第一眼看到的内容在屏幕中间，不再被顶到视口顶端、也不被上边缘裁切。
- **同一查询的后续匹配贴着来向边缘并留出间距**（下方来找底缘、上方来找顶缘），并从边缘移入一小段——连续按「下一个」时匹配一次次从最下方冒出来、上来一点点，方向与操作一致。
- 匹配已经在视口内时完全不动；只差半行时不做动画，直接落位。
- 用户在动画期间滚动（滚轮/触摸/键盘）立即打断动画；系统开启"减少动态效果"时不做动画，直接落位。
- 远距离匹配时，**内容区域**仍会瞬移到目标区域（CodeMirror 虚拟滚动的硬约束：未渲染区域只有估算块高，无法逐帧渲染几千行），但匹配本身仍从边缘移入，不会在顶部闪现。这是本次明确的已知限制。

## User Stories

1. As a JSON 用户, I want 搜索到的匹配落在视口中间, so that 我能一眼看到被找到的内容
2. As a JSON 用户, I want 匹配不再被顶到视口顶端甚至被裁掉一半, so that 匹配文本完整可读
3. As a JSON 用户, I want 视口之外的匹配从视口底缘渐渐升起, so that 我能看清它从哪冒出来、往哪去
4. As a JSON 用户, I want 连续按「下一个」时每个匹配都从视口最下方冒出来, so that 界面不会显得在乱跳
5. As a JSON 用户, I want 搜索后的第一个匹配直接出现在屏幕中间, so that 我不用先滚动找它
6. As a JSON 用户, I want 匹配已经在视口内时画面完全不动, so that 连续搜索时眼睛不用跟着重定位
7. As a JSON 用户, I want 匹配只差一两行时不做长动画, so that 快速连按「下一个」不拖沓
8. As a JSON 用户, I want 动画过程中自绘滚动条平滑跟随, so that 我看得出视口正在移动
9. As a JSON 用户, I want 动画期间可以用滚轮打断, so that 我随时能接管视图
10. As a JSON 用户, I want 用「上一个」时匹配从视口顶缘反向进入, so that 入场方向与操作方向一致
11. As a JSON 用户, I want 替换与全部替换之后落点依然清晰, so that 替换结果可以核对
12. As a JSON 用户, I want 匹配计数、高亮着色、无匹配红框等既有行为保持不变, so that 这次改动不破坏面板现有能力
13. As a macOS 用户, I want Cmd+F 与 Ctrl+F 的匹配跳转表现一致, so that 跨平台行为统一
14. As a 使用"减少动态效果"的用户, I want 搜索跳转不做动画直接落位, so that 我不会被滚动运动干扰
15. As a JSON 用户, I want 重构版的落点分布与源站一致（首个居中、后续贴底）, so that 两个站点之间切换时肌肉记忆仍然有效
16. As a JSON 用户, I want 在几万行的大文档里搜索时界面不卡死, so that 搜索依旧可用
17. As a JSON 用户, I want 搜索面板的替换行、计数与选项按钮照常工作, so that 面板整体行为不被这次改动影响
18. As a 维护者, I want 匹配滚动逻辑独立成一个模块, so that 它不与编辑器主逻辑、滚动条模块纠缠
19. As a 维护者, I want 通过 CodeMirror 官方的搜索配置扩展点接管匹配滚动, so that 不必改动第三方库内部
20. As a 维护者, I want 揭示滚动的关键不变量有源码层回归断言, so that 后续改动不会把落点悄悄改回顶端
21. As a 维护者, I want 行为判定有一份可量化的人工实测清单, so that 动效是否达标有人能复现的验收步骤
22. As a 维护者, I want 新术语写进 GLOSSARY.md, so that 「匹配落点」「揭示滚动」在项目里有统一说法
23. As a 维护者, I want 这次取舍留下一份 ADR, so that 后来者知道为什么不复用编辑器默认的滚动行为
24. As a 维护者, I want 这次改动不新增运行时依赖、不触碰 worker 序列化, so that 产物体积红线与既有验证都不受影响
25. As a 维护者, I want 远距离匹配"内容瞬移"被明确记录为已知限制, so that 它不会被反复当成 bug 排查

## Implementation Decisions

- **匹配落点**定义为：匹配文本在视口中的最终纵向位置。取代 CodeMirror 默认的"贴边可见"（贴边 + 估算高度误差 = 落点偏出视口顶端）。分两种：
  - 一次查询里**第一个需要滚动的匹配**取视口垂直居中（匹配行中心对齐视口中心）；
  - 同一查询的**后续匹配**贴着来向那边视口边缘、朝视口内部退开一段（视口高的 8%，至少一行）。向上查找（上一个）时镜像到顶缘。
- **揭示滚动**定义为：把视口外的匹配从视口边缘移向「匹配落点」的渐次滚动过程。首个匹配不打动画、直接落位居中（用户要的是"出现在屏幕中间"）；后续匹配从边缘移入一小段，让用户看出它从哪个方向冒出来。
- 「首个 / 后续」按**查询标识**判定，不按跳转次数：编辑查询后再按「下一个」重新算首个。首个匹配若本来就完整可见（无需滚动），该次不计入，下一次真正需要滚动时仍按首个处理。
- 揭示动画由 `requestAnimationFrame` 逐帧推进滚动位置，缓动曲线取 ease-out cubic（与源站 Ace 同族：1-(1-e)^3），时长固定约 180ms——起点由实测坐标算出，与落点只差留出的那段间距，距离恒定；匹配与落点相差不足半行时直接落位、不做动画。
- 远距离目标的**内容区域**仍瞬移：CodeMirror 虚拟滚动对未渲染区域只有估算块高，逐帧渲染几千行会卡顿且画面抖动。瞬移只发生在"跳到目标区域"这一步，匹配本身仍走底缘→居中的渐进入场。
- 接管方式：使用 CodeMirror 搜索配置的 `scrollToMatch` 扩展点接管匹配跳转（官方扩展点，不改第三方库内部）。自定义 effect 携带目标范围，由编辑器插件在事务落地后执行。
- 执行顺序至关重要：**先测量、后落位、再动画**。必须先让编辑器把目标区域渲染并测量（否则目标位置的像素坐标是估算值，这正是当前落点跑偏的成因），再在同一帧内把滚动位置改到入场起点，随后逐帧推进到落点。全程在同一帧内完成"跳转 + 起点修正"，避免出现"匹配先闪现到别处、再跳回来"的二次闪动。
- **贴边滚动只用来渲染目标区域，它的落点位置不可信**：折行文档里未渲染区域的估算偏差可达半屏（实测把匹配甩到视口上边 -20px）。因此方向判定（下方来 / 上方来）取"目标内容坐标相对滚动前位置"，动画起点由实测内容坐标自己算，都不采用贴边滚动的停靠位置。
- 打断与降级：动画期间用户滚动（滚轮/触摸/键盘）立即取消动画，用户意图优先；`prefers-reduced-motion: reduce` 时不做动画，直接落位居中；匹配已完全在视口内时不滚动、不动画。
- 与自绘滚动条的关系：动画由滚动位置驱动，自绘滚动条本就监听滚动事件，天然跟随，无需改动其代码。
- 作用范围：仅「编辑器搜索面板」的匹配跳转。GRID 视图定位到编辑器、JSON 校验报错高亮维持现状（两者落点本就是居中）。
- 术语落地：GLOSSARY.md 补「匹配落点」「揭示滚动」两条，并标明与既有「编辑器搜索面板」「浏览器原生查找」的区别。
- 决策留痕：新增一份 ADR，说明为什么不沿用 CodeMirror 默认的匹配滚动（落点贴边 + 瞬移），以及为什么不做全程无跳变的逐行滚动（虚拟滚动硬约束）。
- 不新增运行时依赖，不触碰 worker 序列化与紧凑序列化逻辑，产物体积红线（< 180 kB gzip）不变。

## Testing Decisions

好的测试只验外部可观察行为：匹配在视口中的最终纵向位置、入场过程中滚动位置是否呈现多帧递增序列、动画是否可被打断、降级路径是否直接落位。不断言内部函数名与实现细节。

本仓库无自动化测试套件（CI 只有 build + deploy），沿用既有的两层验证 seam，不引入新框架：

- **自动化 seam（现有）**：源码层代理断言。新增一个回归断言脚本并接入 `npm run verify`，把揭示滚动依赖的不变量固化下来——搜索配置确实被接管（默认的贴边滚动已被替换）、落点计算指向视口居中、动画由 rAF 驱动且使用 ease-out 曲线、用户滚动可打断、`prefers-reduced-motion` 降级存在。先例：`scripts/verify-scrollbar.mjs`（滚动相关的不变量断言）、`scripts/verify-search-keymap.mjs`（搜索相关扩展点顺序断言）。另加 `npm run build`（含 tsc strict）作为类型与构建闸门。
- **浏览器行为 seam（现有约定）**：按仓库既有的人工实测清单形式（`docs/agents/` 下的 browser-checklist 文档），给出可量化验收值：首个匹配落点位于视口高度的 40%~60% 区间；后续匹配落点位于 85%~95% 区间（向上查找镜像到 5%~15%）；匹配文本完整落在视口内（纵坐标不为负、底边不出视口）；后续匹配的揭示期间滚动位置出现多帧序列而非单帧跳变；`prefers-reduced-motion` 下直接落位。先例：`docs/agents/browser-checklist-grid-no-truncation.md`。

明确不做：不引入浏览器自动化测试框架（与本仓库"零自动化测试套件 + 静态断言 + 人工清单"的约定冲突），不为本次改动新增运行时依赖。

## Out of Scope

- GRID 搜索面板、GRID 视图定位到编辑器、JSON 校验报错高亮的动画化（后两者落点本就是居中，本次不动）。
- 让远距离匹配全程无跳变（逐行渲染几千行），以及由此产生的"内容瞬移"消除。
- 替换编辑器搜索面板为自研实现（仍是复刻原站 Ace searchbox）。
- 匹配计数、高亮着色、替换语义、无匹配红框等既有能力的改动。
- 浏览器自带查找（作用于已渲染 DOM 文本）的任何行为。
- 引入浏览器自动化测试框架、新增运行时依赖、调整产物体积红线。

## Further Notes

- **本次调查的实测基线**（同为"首个匹配在视口之外"的场景，视口高度 812px / 840px）：
  - 本地重构版（CodeMirror 6）：落点 y = -20px（视口顶端之上，被裁切）；滚动位置单帧从 0 跳到 1065.6，无中间帧。
  - 源站 jsongrid.com（Ace 1.31.1）：首个匹配落点 y = 403/840（48%，居中）；随后一次查找落点 y = 806/840（贴底缘）；滚动位置 1314 → 3031 → 2628，两步。
- **源站的落点机制**：Ace 的 `revealRange(range, .5)` → `scrollSelectionIntoView(start, end, .5)`，其中 0.5 是居中修正系数；第二次对同一行末尾再调一次滚动时拿到的是过期滚动值，于是落点退化成"贴底缘"。我们只取"居中"这一确定性结果，不照抄这个副作用。
- **源站本身没有动画**：实测其 `animatedScroll` 为 false（Ace 默认值），所谓"渐渐升起"是落点差造成的观感。"渐进入场"是本次的增强项，不是对源站的复刻。
- **主要技术风险**：CodeMirror 对未渲染区域使用估算块高，若在测量完成前计算落点，落点会偏出视口——这正是当前 bug 的成因。因此"先测量、后落位"的执行顺序是本方案的关键约束，必须由回归断言守住。
- 术语：见仓库 GLOSSARY.md（本次新增「匹配落点」「揭示滚动」）；相关既有术语「JSON 编辑器」「编辑器搜索面板」「GRID 搜索面板」「浏览器原生查找」在本次范围内不冲突。
